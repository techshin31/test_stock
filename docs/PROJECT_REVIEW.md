## 계산 규칙과 운영상 제한

CAGR 입력은 거래일별 행을 갖는 자산 곡선이어야 한다. 중간 결측 행은 계산 기간에
포함하지만, 애초에 인덱스에 없는 거래일은 추정하지 않는다. 거래일 그리드가 누락된
입력은 호출자가 먼저 맞춰야 한다. 수정된 기간 규칙에 따라 과거 백테스트의
CAGR·Calmar가 달라질 수 있으며, 저장된 과거 보고서를 임의로 재작성하지 않았다.

응답 확인 시각은 시세 관측 시각과 다르다. 대시보드는 마지막 성공 요청과 갱신
오류를 보여주며, 시장 데이터의 실제 관측일과 출처는 각 화면에서 확인한다.

매매 전략과 주문 안전 조건은 변경하지 않았다. PAPER/REAL 주문이나 스케줄러를
시작하지 않았고, 외부 수집·증권 API를 검증하지 않았다. 개발용 DB는 현재 환경의
PostgreSQL 16.2를 사용했으며 CI는 공식 PostgreSQL 16 이미지를 사용하도록 구성했다.
DB 연결 실패의 종목명 캐시 재시도 정책과 나머지 대형 모듈 분리는 이번 범위 밖이다.

## 2026-10-02 실제 데이터 검증 후 전략·캐시 수정

실제 가격으로 백테스트를 실행하자 `RiskNeutralStrategy`가 정의되지 않은
`_calc_indicators()`를 호출해 중단됐다. `AggressiveStrategy`에서도 같은 오류를
회귀 테스트로 재현했다. 이전 리팩터링에서 삭제된 `AbstractStrategy`의 공통
ATR·볼린저 밴드·MA10 계산을 복원하고, 단기·중기 MA는 국면 계산 결과를 재사용한다.
진입 비중·청산 규칙·주문 정책은 바꾸지 않았다.

분석 캐시는 준비도 요약의 최신 날짜만으로 입력 변경을 판단했다. 실제 매크로
데이터가 658행에서 7,788행으로 늘어도 결과가 비어 있는 기존 run을 재사용했다.
이제 준비도·설정·실행 날짜 외에 기준일 내 원천 데이터의 행 수와 내용 SHA-256을
캐시 키에 포함한다. 매크로, WICS 구성종목·업종 지수·종목 가격, 재무제표, 기업 정보,
기업 위험 상태를 비교하며, 분기 FA 점수를 재사용하는 실행은 해당 모델의 점수 원장도
비교한다. PostgreSQL이 원천 내용을 해시하므로 Python으로 전체 이력을 전송하지 않는다.

보충·정정·삭제·revision 추가는 캐시를 무효화한다. 기준일 이후 발표된 매크로와
같은 값의 단순 재수집은 이전 결과를 재사용한다. 업종 가격의 `collected_at`과
재사용 FA 원장의 `id`는 실제 원천 선택의 우선순위·참조에 쓰이므로 비교에 유지한다.
새 키는 기존 키와 달라 첫 실행에서 새 run이 생성되며, 기존 분석·발행 이력은 보존한다.
내용 해시는 기준일 내 원천을 읽고 정렬하므로 대규모 이력에서의 DB 부하는 별도 측정이 필요하다.

## 2026-10-02 DART 수집 실패 처리 수정

DART 재무제표 API의 `020`(요청 제한)·인증 오류를 빈 데이터로 처리했고,
공시 API는 페이지 수집 중 오류가 나면 이전 페이지의 일부 결과를 반환했다.
로더도 기업별 요청 실패를 경고로만 처리해 수집 명령이 성공으로 종료될 수 있었다.
이제 정상적인 자료 없음(`013`)과 호출 제한·인증·HTTP·연결·응답 형식 오류를 구분한다.
`corpCode.xml`이 ZIP 대신 반환하는 XML 오류도 같은 분류로 처리한다.

실패 시 해당 수집을 즉시 중단하고 워커는 종료 코드 1을 반환한다. 자동 재시도로
추가 호출을 발생시키지 않는다. 이미 저장한 기업·보고서 버전은 유지하므로 연결 복구 후
기존 캐시·증분 수집을 이용해 재개한다. 원래 HTTP 예외나 원격 메시지는 출력하지 않아
API 키가 포함된 요청 URL이 로그와 traceback에 노출되지 않도록 했다.

- 추가 회귀 테스트 **40개**, 기존 시점 수집 테스트 포함 **65개** 통과.
  호출 제한·인증 오류, HTTP 429·502·503, 연결 실패, 잘못된 JSON,
  XML 오류·정상 ZIP, 공시 페이지 중간 실패, 정상 수집 및 CLI 종료·DB 정리를 검사했다.
- 전체 Python 테스트 **448개 통과**.
- 실제 재무 수집 명령은 `corpCode.xml` 요청에서 `PROXY, HTTP 502`를 표시하고
  종료 코드 1로 중단됐다. 기업·공시·재무 원천은 0행이며 재무 데이터 검증 통과를 의미하지 않는다.

DART 키 바인딩 저장 및 워커 주입은 확인됐다. 키 없는 API·홈페이지 요청과
브라우저 User-Agent 요청도 동일한 프록시 502였고, WICS 공개 요청은 HTTP 200이었다.
현재 응답으로 DART의 인증 상태나 일일 호출량을 판정할 수 없다. 프록시의 상위 연결
실패는 재현했지만 상세 프록시 로그에 접근할 수 없어 원격 서버·접속 차단·프록시 장애 중
근본 원인은 확정하지 않았다. 클라우드 측 `opendart.fss.or.kr:443` 접속 경로 확인이 필요하다.
로그는 `dart-fixed-python-tests.log`, `dart-fixed-collection.log`에 저장했다.

## 2026-10-03 재무 원천 검증·준비도·거래 로그 날짜 수정

분기별 재무 API는 접수번호 대신 기업·사업연도·보고서 코드로 최신 원본을 요청한다.
기존 로더는 응답의 `rcept_no`를 검사하지 않고 DB에서 선택한 공시 접수번호·이용 가능일을
기록했다. 이제 저장 전에 모든 계정 행의 기업·사업연도·보고서 코드·접수번호를 대조한다.
후일 정정 데이터가 이전 공시 데이터로 저장되는 것을 막으며, 불일치 시
`SOURCE_MISMATCH`로 중단한다. API 응답에서 생략될 수 있는 `fs_div`는 요청값을 유지하고,
응답에 존재할 때 추가 대조한다. 기존 데이터나 수집하지 못한 역사 버전을 임의로 재작성하지 않는다.

재무 준비도는 접수번호 8개를 분기 8개로 세고, 미등록 기업은 분모에서도 제외했다.
이제 기준일 안의 CFS를 사업연도·보고서별 한 분기로 묶어 가장 최신 버전만 검사한다.
정정공시 여러 건이나 OFS가 분기를 늘리지 않는다. 최신 버전의 BS·IS/CIS·CF 구성과
원천 공시의 기업·접수일·이용 가능일·보고 기간을 확인하고, 미등록·시장 미확인 대형주도
분모에 유지한다. 이 지표는 최소 8분기 보유 여부이며, 최근 필요한 8분기와 비12월 결산
기업의 보고 기간 검증은 실제 수집 후 별도로 수행해야 한다.

전체 테스트는 UTC 서버에서 거래 이력을 쓰면서 한국 날짜로 체결 상태를 보정하던
추가 오류를 재현했다. 새 거래 이력과 보정 이벤트는 `+09:00`을 포함한 한국 시각으로
저장한다. 시간대가 있는 기존 로그는 한국 날짜로 비교하고, 시간대가 기록되지 않은
과거 로그는 임의로 UTC 또는 한국 시각으로 해석하지 않고 기존 날짜 의미를 유지한다.
주문 제출·체결 정책은 변경하지 않았으며 PAPER/REAL 주문을 실행하지 않았다.

검증 결과:

- 관련 수집·준비도·거래 이력 테스트 **134개 통과**, 전체 Python **468개 통과**.
- PostgreSQL **27개 통과**. 고유 임시 DB에서 정정공시 중복, CFS/OFS 구분,
  최신 정정본의 누락, 미래 정정 제외, 이용 가능일·원천 오류, 미등록 기업 포함을 검사했다.
- 현재 환경의 실제 API·대시보드 DB 건강 검사 모두 HTTP 200이다.
- 실제 기업·공시·재무 수집은 첫 `corpCode.xml`에서 `PROXY, HTTP 502`로 exit 1을 반환했다.
  기업·공시·재무·분기 FA는 각각 0행이며, 준비도는 WARNING이다.

키 저장·주입과 unrestricted 네트워크 정책은 계속 확인됐다. Open DART HTTPS의
인증 요청과 홈페이지는 502지만, 일반 DART `https://dart.fss.or.kr/`는 HTTP 200,
Open DART의 키 없는 HTTP 홈페이지는 HTTPS로 정상 302 전환했다. TLS 1.2와 HTTP/1.1로
검증한 공개 HTTPS 요청도 동일한 502였다. 비밀 값은 HTTPS 표준 경로에서만 사용했다.
장애는 Open DART HTTPS 접속 경로에 한정해 재현됐지만 상세 프록시 로그 접근 기능이
없어 상위 TLS 연결·원격 접속 차단·프록시 문제 중 근본 원인은 아직 확정할 수 없다.
실제 DART 인증 결과·일일 호출 한도·재무 원천 검증은 완료되지 않았다.
진단과 실행 로그는 `/workspace/cloud-setup/validation-20261003`에 저장했다.

## 2026-10-03 자동 실행 준비도 감사 보완

현재 클라우드에서 `system_readiness --require-complete`를 실행하자 PAPER dashboard
기록 부재로 예외 종료하고 보고서를 남기지 않았다. 새 환경·손상된 JSON은 이제
안전/완료/실전 승인 모두 false인 BLOCKED 보고서를 원자적으로 저장하고 exit 2를 반환한다.
이전 성공 보고서가 이번 실패 뒤에도 남는 문제를 회귀 테스트로 검사했다.
핵심 감사 함수의 실제 관측·체결 표본·PAPER 기간 조건은 유지했다.

`python -m apps.worker readiness --cutoff YYYY-MM-DD --require-ready`를 추가했다.
수집·분석·발행·주문 없이 현재 원천 준비도를 검사하고 PASS 이외에는 exit 2로 중단한다.
기존 `collect all --check-readiness`의 보고서 전용 동작은 유지한다.
실제 현재 입력 검사와 운영 감사는 각각 WARNING/BLOCKED와 exit 2를 반환했다.
현재 KIS PAPER 인증 변수는 주입돼 있지 않으며, DART는 계속 PROXY HTTP 502다.

관련 준비도·CLI·수집 테스트 60개가 통과했다. 이 보완으로 외부 데이터 수집이나
PAPER 실운영 관측이 완료된 것은 아니며, 시스템 전체 완료는 남은 외부 조건으로 차단된다.

전체 Python 회귀 테스트는 **482개 통과**했다.

## 2026-10-03 HTTPS 프록시 및 FA 백테스트 추가 진단

DNS는 클라우드·Google·Cloudflare 모두 같은 Open DART 주소로 확인됐고,
클라이언트에서 제공된 프록시까지의 CONNECT·TLS 인증서 검증은 정상이다.
공식 영문 Open DART는 같은 IP·인증서 체인·TLS 1.2 암호군을 사용하면서 이 프록시에서
홈페이지 200, 키 없는 `/engapi/company.json` status 100을 반환했다.
외부 SSL Labs도 한국어·영문 호스트 모두 HTTPS 200과 정상 인증서 신뢰 경로를 확인했다.
따라서 한국어 호스트의 프록시 상위 경로를 점검해야 하며, 서버의 RSA/DHE 암호군
특성만으로 근본 원인을 확정하지 않았다. 프록시 상세 로그·설정 변경 도구는 제공되지 않는다.

실제 `risk_neutral`, `fa-published`, 2025-01-02~2026-10-02 백테스트를 실행했으나
시작일 이전 PUBLISHED FA 유니버스가 없어 exit 1로 중단됐다. 실제 재무와 분기 FA는
여전히 0행이며 WICS 구성·가격 이력도 부족하다. 성과 보고서는 생성되지 않았다.
백테스트 실행 시 쓰기 불가능했던 폰트 캐시는 `XDG_CACHE_HOME`을 쓰기 가능한 위치로
설정해 해결하고 재실행으로 확인했다. 환경 설치·시작 설정에 저장했으며 서비스 건강
검사도 통과했다. 이 환경 수정은 502 복구를 의미하지 않는다.

비밀 값 없는 비교 증거·클라우드 지원 점검 요청·실제 실행 로그는
`/workspace/cloud-setup/validation-20261003/proxy-investigation/report.md`에 있다.

## 2026-10-03 초기 자동매매 개발 기반 구축

기존 수집·분석·매매 구성에 초기 설치와 격리 검증 경로를 추가했다.
`storage.postgres.bootstrap`은 빈 DB의 스키마·시드를 한 트랜잭션으로 설치하고
후속 마이그레이션을 적용한다. 기존 완전한 DB는 반복 실행해도 유지하며,
불완전한 비어 있지 않은 DB는 초기화를 거부한다. 실제 임시 PostgreSQL DB에서
반복 실행, 기존 데이터 보호와 SQL 실패 시 전체 롤백을 검증했다.

`apps.system doctor`는 DB를 읽기 전용으로 진단하고 개발 준비도와 데이터 준비도를
구분한다. 키는 존재 여부만 표시하고 브로커를 초기화하지 않는다.
`apps.system local-check`는 합성 입력·임시 가상계좌로 실제 FA/TA 전략, 투자 한도,
주문 계획, DRY_RUN 무체결, 비용 포함 체결, 재시작 중복 방지, 손절·진입 차단기,
과매도 거부와 현금 정합성 등 13개 검사를 수행한다. 이 결과는 실제 FA 백테스트
성과를 의미하지 않는다. 임시 계좌는 검사 뒤 삭제한다.

직접 Trader CLI의 기본 모드는 DRY_RUN이며 주문 핵심 함수에서도 차단한다.
Telegram 알림은 직접 CLI의 `--notify`로 활성화한다. 가상 브로커는 유한한 양수 가격,
양의 정수 수량과 비용률을 검증하고, 저장이 성공하기 전에 메모리 잔고를 변경하지
않는다. 가상 체결 식별 키를 저장해 재시작 뒤에도 같은 주문을 다시 청구하지 않는다.
소수 수량의 정수 절삭과 잘못된 주문 방향의 매도 처리도 거부하도록 수정했다.

최종 검증은 Python 단위·회귀 **523개**, PostgreSQL 연동 **30개**, 브라우저 **7개**가
모두 통과했고 대시보드 lint·build도 성공했다. 현재 실제 DB의 초기 설정 반복 실행과
읽기 전용 진단은 성공했고 개발 준비도는 true다. 데이터 준비도는 WARNING이며
실제 재무·분기 FA·발행 FA 유니버스는 여전히 없다. HTTPS 프록시 502와 KIS 인증정보
미설정, 실제 FA 백테스트 및 운영 관측은 별도 남은 조건이다. 이번 구축·검증 과정에서
PAPER/REAL 주문 또는 scheduler를 실행하지 않았다.

실행 순서는 [초기 구축 가이드](TRADING_SYSTEM_START.md)에 정리했다.
